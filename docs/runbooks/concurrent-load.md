# 并发压测、排队延迟与超时核查

适用范围：XIAOTAO本地模拟实验室，Python 单进程、单副本，SQLite 或待验证的 MySQL。并发压测仅操作合成资金。

## 发起和观察

从“并发压测”页面选择转账、支付、充值、提现或同一幂等键重放。先用 20 并发、200 请求建立基线，随后逐级增加并发。每次会创建专用账户，准备资金后通过真实 HTTP 调用交易 API。每个客户端等待上次请求返回，再提交下一笔，因此它是闭环负载，不是固定每秒请求量的流量模型。

请求 RPS = 已返回或超时的请求数 / 请求测量窗口；已确认 TPS = 成功响应中去重后的交易编号数 / 测量窗口。幂等重放可以有较高 RPS，但不能算作新增交易。P95/P99 是客户端观测延迟，包括连接、服务端排队和响应。账户准备、进程启动和结束对账不计入测量。各请求针对一对热点账户，不代表大量独立账户的全场景容量。

## 吞吐下降、尾延迟升高

现象：提高并发数后 TPS 不升反降，P95/P99 上升。当前写锁会让交易串行记账，线程池、SQLite 写锁、同步日志及本机资源竞争也可能带来排队。并发客户端数不代表同时提交到数据库的事务数。先比较相同场景、金额、数据规模和机器状态下的报告，再结合日志判断；单凭压测指标不能证明具体根因。

使用错误样本中的 Trace ID 到“日志检索”查看事件；进入“根因分析”限定 Trace ID 或时间范围，区分依赖延迟、连接获取超时与提交后响应丢失。只有规则证据不足时，继续排查进程、数据库连接和系统指标。当前平台尚未采集底层 TDSQL/赤兔和 Linux 主机指标，不能据此宣称底层故障已定位。

## 停止与未确认结果

停止操作、达到请求总量或最大发压时长后不再安排新的请求。已发送请求不会撤销记账，会等待返回或客户端超时。请求超时和 HTTP 504 可能发生在账务提交之后；报告会计入未确认结果。此时已确认 TPS 可能小于实际入账笔数。

1. 保存报告中的任务编号和错误样本幂等键，必要时使用 LT-任务编号-请求序号定位其余请求，序号从 0 开始；幂等重放场景全部使用序号 0。
2. 在“交易中心”按原幂等键查询状态，关联 Trace ID 检查 LEDGER_COMMITTED 和 RESPONSE_TIMEOUT 等事件。
3. 等待在途请求稳定后在“账务与对账”重新核对。一次平衡快照不能证明超时请求全部执行完毕。
4. 需要重试时使用原幂等键及完全相同的正文，禁止换键直接重扣。

服务重启会请求旧任务停止；报告失联会标记中断，不会自动恢复发压。压测产生的账户、流水、分录和日志保留用于追溯。

## 故障对照实验

建立无故障基线后，在“故障演练”启用限时依赖延迟、依赖不可用、连接获取超时或记账后响应丢失，再用相同压测参数观察。故障仅影响应用交易 API；账户准备阶段不受注入影响。演练结束或手动停止后重新测量，验证恢复。

本机结果不能作为 TDSQL、CCE 或生产容量结论。迁移后需要真实环境验收、逐级加压、长时间稳定性测试和数据库指标支持；首版禁止直接增加应用进程或副本。
