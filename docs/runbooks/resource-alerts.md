# XIAOTAO 容器资源不足与告警排查

适用范围：独立 Docker 资源演练环境，cgroup v2；账户和交易均为模拟数据。

## 指标含义

CPU 百分比以本容器 CPU 配额为分母。例如上限 0.5 核，用量 0.4 核就是 80%。CPU 限流累计时间支持排队原因候选，不代表当前正在发生故障。容器 CPU 和内存包括同容器内的 HTTP 发压子进程。

内存采用 memory.current / memory.max，包含缓存和 tmpfs，和 Docker stats 的工作集显示不同。没有显式配额时不伪造百分比。OOM kill 可能先杀死发压子进程；容器重建会重置 cgroup 计数，因此没有 OOM 指标不能证明未发生 OOM。

capacity 是有真实容量上限的 tmpfs 临时文件系统，占用容器内存；它用于容量告警演练，不是 MySQL 持久化数据盘。data 是应用数据所在共享文件系统，其总容量不是该容器的专属磁盘配额。

## 观察步骤

1. 在资源与告警页检查当前配额、采样时间、监控连接状态。
2. 在并发压测页发起 100 并发、10000 请求、最长 90 秒、请求超时 30 秒的受限实验；预期可能超时、失败或触发 OOM，不能保证固定 TPS。
3. Prometheus 每 5 秒采集；CPU 使用率先经过 30 秒窗口计算，再持续超过 80% 达 20 秒后触发。pending 表示条件成立但持续时间不足；firing 才是正式告警。
4. 检查 P95、错误率和限流计数是否在同一时段上升。相关性只是原因候选。
5. 停止继续发压并等待在途请求结束，观察恢复，再执行账务核对。客户端超时必须按原幂等键查询，不要换键重复提交。

容量实验可以独立填充至 85%，持续 60 秒；到期清理或手动清理后，等待下一次规则评估。不要与大内存压测同时开始。

## 告警证据与监控故障

告警触发和恢复写入应用 monitoring 日志，可在根因分析和运维助手关联现场证据。应用不可用时其页面和日志不能工作，请使用独立 Prometheus 的 Alerts 页面。Prometheus 不可达时页面显示过期状态，不把旧告警当作实时结果。进程恢复后只能记录恢复时可见的状态，不能补齐宕机期间所有瞬时事件。

只提供平台内和 Prometheus 告警；邮件、企业微信等外部通知尚未配置。
